# TASK: BUILD A PRODUCTION-GRADE LOCAL PR REVIEW SKILL FOR THIS PLAYWRIGHT FRAMEWORK

You are a Principal Software Development Engineer in Test (SDET),
Senior TypeScript Engineer, Playwright Framework Architect, and
experienced Code Review Engineer.

Your task is to design, implement, document, and validate a
comprehensive Claude Code skill named:

/pr-review

This skill must perform a rigorous, evidence-based LOCAL pull
request review of the current Git branch in this repository.

The review must be comparable to a thorough review performed
by a highly experienced Senior SDET or QA Automation Architect.

IMPORTANT:

Do not simply generate a generic SKILL.md.

You MUST first investigate the existing Playwright framework,
understand its architecture, identify its established conventions,
and then create a repository-specific PR review skill.

The implementation must be production-ready, maintainable,
accurate, reusable, and compatible with the existing framework.

Do not modify existing application code or test implementations
unless explicitly authorized.

Do not introduce unnecessary dependencies.

Do not assume this repository uses the same architecture,
tools, services, or conventions as another Playwright project.

============================================================
PART 1 — OBJECTIVE
============================================================

Create a Claude Code skill that allows developers to execute:

/pr-review

The skill must automatically:

1. Identify the current Git branch.
2. Determine the correct base branch.
3. Identify committed changes belonging to the PR.
4. Collect changed files and commit information.
5. Classify the scope and risk of the changes.
6. Analyze the modified code in depth.
7. Execute applicable automated static checks.
8. Validate Playwright testing best practices.
9. Validate TypeScript coding standards.
10. Verify framework architecture compliance.
11. Identify bugs, security risks, and reliability problems.
12. Detect missing or weak assertions.
13. Verify test data creation and cleanup.
14. Evaluate maintainability and code quality.
15. Detect potential flaky test patterns.
16. Distinguish newly introduced defects from existing issues.
17. Generate a detailed, structured review report.
18. Provide an evidence-based review decision.
19. Ask whether the developer wants to execute tests.
20. Update the review based on test results.
21. Ask whether the developer wants to save the report.
22. Support subsequent reviews after fixes are committed.

The skill must work locally.

Creating or opening a remote pull request must NOT be required.

Remote APIs may be used to resolve PR metadata when configured
and available, but the review must remain functional offline
using local Git information.

PART 7 — GIT BASE BRANCH RESOLUTION
============================================================

Correctly determining the base branch is CRITICAL.

Do not blindly compare against:

main

master

develop

or the highest-version release branch.

Determine the actual PR destination.

Use the following priority:

1. Explicit base branch supplied by the developer.

2. Destination branch from the current PR metadata,
   when a supported Git provider is configured.

3. Repository-specific documented branching conventions.

4. Remote default branch, when appropriate and verified.

5. Other evidence from local Git history.

If the base cannot be determined confidently, ask the
developer to select the correct branch.

Never silently choose an uncertain base.

Support repositories using:

- main
- master
- develop
- release/*
- feature/*
- hotfix/*
- other custom branching strategies

Verify that the selected Git reference exists.

Determine the merge base when appropriate.

Use the three-dot comparison for PR changes:

git diff BASE...HEAD

Avoid including unrelated commits from other branches.

Validate the comparison using:

git merge-base BASE HEAD

git rev-list --count BASE..HEAD

git diff --stat BASE...HEAD

git diff --name-only BASE...HEAD

Use repository-appropriate references.

Do not assume a remote branch exists locally.

Do not automatically fetch remote branches without
considering network availability and user permissions.

If a remote fetch is needed, explain why.

If local Git references are broken, report the problem.

Do not claim a review is complete when the comparison
cannot be established reliably.

============================================================
PART 22 — REVIEW DECISION MATRIX
============================================================

Use the following review decisions:

APPROVED

CHANGES REQUESTED

REJECTED

INSUFFICIENT EVIDENCE

Decision rules:

REJECTED:

One or more confirmed CRITICAL findings exist.

CHANGES REQUESTED:

No critical findings exist, but one or more
IMPORTANT blocking findings remain.

APPROVED:

No confirmed blocking findings remain.

All mandatory applicable checks have passed.

Any remaining issues are minor or informational.

INSUFFICIENT EVIDENCE:

A mandatory check could not be completed and
the missing evidence prevents a reliable approval.

Additional rules:

- Passing tests do not automatically override code defects.
- Unverified checks must never be represented as passing.
- Not applicable checks must not count as successful checks.
- Protected files may require mandatory human approval.
- Existing technical debt must be distinguished from PR defects.
- External service failures must be reported separately.
- The review must never claim that tests ran when they did not.

If tests were not executed, explicitly state:

"Test execution was not performed."

If the review is otherwise complete, explain that
the approval is based on static review only.

Failing tests must be investigated before assigning severity.

Environment failures must be distinguished from code defects.

Flaky failures must not automatically be treated as
confirmed deterministic defects.

A confirmed critical defect must continue to block approval.

If the test results are inconclusive, report that explicitly.

PART 28 — FALSE POSITIVE PREVENTION
============================================================

Accuracy is more important than the number of findings.

Implement the following safeguards:

1. Never report a defect based only on grep output.

2. Inspect surrounding code.

3. Verify that the issue is introduced by the PR.

4. Respect repository-specific conventions.

5. Do not flag valid Playwright patterns unnecessarily.

6. Do not require assertions in helper functions
   when assertions belong in the calling tests.

7. Do not require cleanup for resources that are
   intentionally persistent.

8. Do not require random test data for legitimate
   fixed-value scenarios.

9. Do not report unavailable checks as passing.

10. Do not claim complete coverage without evidence.

11. Do not fabricate line numbers.

12. Do not confuse existing issues with new defects.

13. Do not treat test discovery as test execution.

14. Do not treat successful compilation as proof
    of functional correctness.

15. Do not approve a PR solely because tests pass.

16. Do not report speculative concerns as confirmed bugs.

17. Explain uncertainty when evidence is incomplete.

18. Prioritize findings with real engineering impact.

============================================================
PART 29 — PERFORMANCE AND EFFICIENCY
============================================================

The review must be thorough without being unnecessarily slow.

Optimize the workflow by:

- Classifying changed files first
- Running only applicable checks
- Reusing existing validation scripts
- Avoiding repeated Git commands
- Avoiding unnecessary full-repository scans
- Inspecting directly related dependencies
- Skipping irrelevant integration checks
- Avoiding redundant test execution

However:

Do not sacrifice correctness for speed.

Do not skip mandatory checks merely to finish faster.

When the PR is large, prioritize critical and high-risk
changes while clearly reporting any unreviewed areas.
